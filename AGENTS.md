# Правила работы с репозиторием

## Структура проекта и модули

- `jarvisd/`: сервис колонки, обработка звука, интеграции ассистентов и встроенная веб-панель в `ui/`.
- `hardware/`: общее определение модели колонки; `installer/`: установщик со встроенным интерфейсом и генерируемым каталогом `payload/`.
- `plugins/`: манифесты официальных плагинов, реализации на JavaScript и нативные Go-модули в `*/src/`; `pluginsdk/`: SDK нативных плагинов.
- `station/`: вспомогательные программы на C для микрофона и сервисные скрипты; `models/`: веса распознавания слова активации; `kws/`: инструменты обучения.
- `scripts/`: утилиты упаковки; `docs/`: документация по сборке, плагинам, приватности и выпускам. Go-тесты расположены рядом с исходниками.
- `.agents/skills/`: локальные скиллы проекта и их справочные материалы.

## Сборка, тестирование и разработка

Используйте версию Go из `go.mod` соответствующего модуля. Корневого Go-модуля нет: выполняйте команды Go в нужном каталоге. Примеры рассчитаны на POSIX-оболочку; в Windows используйте WSL или Git Bash.

- `cd jarvisd && go vet ./... && go test ./...`: статическая проверка и тестирование сервиса.
- В `hardware/` выполняйте `go test ./...`; в `pluginsdk/` и каждом `plugins/*/src/` — `go vet ./... && go test -race ./...`.
- Из `jarvisd/`: `go run . -data ../devdata -listen 127.0.0.1:8080 -ui ui` запускает сервис для локальной разработки панели. Проверка звука требует самой колонки.
- Из корня: `sh build.sh` собирает программы колонки, вспомогательные компоненты и установщик Windows. Нужны Go и Zig; результат находится в `build/` и `installer/payload/`.
- `RELEASE=1 sh build.sh` создаёт файлы выпуска в `build/release/`. Тесты установщика запускайте после генерации `payload/`.
- `go run scripts/pack-plugins.go build/plugins` упаковывает официальные плагины и собирает все их нативные модули под ARM; Zig и payload установщика для этой команды не нужны.

## Установщик: `installer/`

Отдельный Go-модуль `jarvissetup` открывает локальную страницу в браузере, ищет колонки и устанавливает, обновляет или удаляет Джарвиса. Для работы нужна уже разблокированная колонка с root и сетевым ADB на порту 5555.

- `main.go`: HTTP API, поиск устройств и операции установки; `adb.go`: собственный ADB-клиент без зависимости от `adb.exe`.
- `hardware.go`: проверка окружения колонки и ABI микрофонной библиотеки; общая идентификация моделей находится в `../hardware/`.
- `cleanup.go`: обнаружение известных модов и план очистки. При изменениях сохраняйте защиту системных файлов, root, ADB, SSH и Entware.
- `ui/`: HTML, CSS, `setup.js` и ресурсы интерфейса; `install.sh` и `install.ps1`: скрипты установки.
- `ui/` и `payload/` встраиваются через `go:embed`; содержимое `payload/` формируется корневым `build.sh`.

После сборки выполняйте из `installer/` команды `go test ./...` и `go run .`. Для фиксированного локального адреса и запуска без браузера: `JARVIS_SETUP_ADDR=127.0.0.1:8090 JARVIS_SETUP_NOBROWSER=1 go run .`. Синтаксис интерфейса проверяйте из корня: `node --check installer/ui/setup.js`. Регрессионные проверки находятся в `cleanup_test.go` и `hardware_test.go`.

## Разработка плагинов и локальные скиллы

Для задач с плагинами используйте [yajavis-plugins](.agents/skills/yajavis-plugins/SKILL.md): JS API, Go SDK, манифесты, тесты и упаковка. Для неофициального плагина в собственном репозитории дополнительно прочитайте [руководство](.agents/skills/yajavis-plugins/references/unofficial.md).

Официальные плагины размещайте в `plugins/<id>/` и согласовывайте версии с `plugins/index.json`. Для отдельного репозитория используйте его собственный модуль и архивы `jarvis-plugin*.zip`; официальный каталог YaJavis там не нужен.

Скиллы храните как `SKILL.md` и необходимые справочные Markdown-файлы. Не добавляйте файлы, специфичные для конкретного harness, включая `agents/openai.yaml`. Объёмные инструкции выносите в `references/` со ссылками из `SKILL.md`.

## Стиль кода и именование

Форматируйте Go через `gofmt` с табуляцией. Используйте MixedCaps для идентификаторов и понятные имена файлов в нижнем регистре. Сохраняйте платформенные суффиксы файлов и теги сборки. В JavaScript панели придерживайтесь отступов в два пробела. Панель использует ES-модули без сборщика: состояние изменяет только объявивший его модуль, запуском управляет `main.js`. Интерфейсы плагинов описаны в `docs/PLUGINS.md`.

## Требования к тестам

Используйте пакет `testing`, файлы `*_test.go` и имена вида `TestFeatureBehavior`. Для исправлений добавляйте целевые регрессионные тесты, для изменений конкурентного кода — проверки гонок. Набор таких проверок сервиса в CI указан в `.github/workflows/test.yml`. Минимальный процент покрытия не задан. Сетевые проверки включаются явно через `JARVIS_NET=1`. Отдельно указывайте результаты автотестов, проверок на колонке и обращений к реальным сервисам.

Обычный CI проверяет модули, синтаксис JavaScript и упаковку плагинов. Тесты установщика выполняются в `.github/workflows/release.yml` после сборки payload. Для ES-модулей панели CI копирует каждый `jarvisd/ui/js/*.js` во временный `.mjs` и запускает `node --check`.

## Коммиты и запросы на слияние

В истории используются префиксы `fix:`, `fix(ui):`, `test:`, `ci:` и номера версий для выпусков. Ограничивайте коммит одной задачей. В PR описывайте изменение поведения, прикладывайте ссылки на связанные задачи, результаты проверок и ограничения; для изменений панели добавляйте скриншоты. Для выпуска нужен `docs/releases/<version>.md` по шаблону `.github/RELEASE_TEMPLATE.md`.

## Безопасность и настройки

Не добавляйте в Git ключи, токены, `settings.json`, записи звука и личные данные приложения. Для локальных данных используйте игнорируемый каталог `devdata/`. Не включайте в коммиты сгенерированный `payload/` и бинарные файлы.
