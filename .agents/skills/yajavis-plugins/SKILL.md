# Разработка плагинов YaJavis

Скилл охватывает плагины внутри YaJavis и в отдельных репозиториях. Команды с переменными окружения рассчитаны на POSIX shell; в Windows используй WSL/Git Bash или эквивалентный синтаксис PowerShell.

## Выбор места разработки

- **Официальный плагин в YaJavis**: используй `plugins/<id>/`, `plugins/index.json` и корневой упаковщик. Пути и команды ниже относятся к корню YaJavis, если не указано иное.
- **Неофициальный плагин в собственном репозитории**: прочитай [references/unofficial.md](references/unofficial.md). Там описаны структура отдельного проекта, зависимость от SDK, тесты, ZIP и публикация в каталоге. Применяй общие правила API ниже; не создавай в таком проекте официальный каталог и не переноси туда сборку всего YaJavis.

Для существующего проекта сохраняй его структуру. Учитывай его собственный `AGENTS.md`, если он есть.

## Выбор реализации и источники

В checkout YaJavis прочитай корневой `AGENTS.md` и нужные разделы [docs/PLUGINS.md](../../../docs/PLUGINS.md). Для существующего плагина сначала изучи его `plugin.json`, исходники и тесты. Сохраняй выбранный язык и архитектуру, если задача не требует их менять.

- **JS**: команды, справочная информация и HTTP-интеграции без доступа к файловой системе и процессам. Примеры: [dice](../../../plugins/dice/main.js), [weather](../../../plugins/weather/main.js), [currency](../../../plugins/currency/main.js).
- **Native**: отдельный процесс, системные зависимости или провайдер ядра. Go-код официального плагина находится в `plugins/<id>/src/` со своим `go.mod`. Пример структуры: [home](../../../plugins/home/src/main.go); публичный SDK: [pluginsdk](../../../pluginsdk/pluginsdk.go).

Когда документация и код расходятся, проверь реализацию: `jarvisd/plugins.go` — валидация, каталог и установка; `jsplugin.go` — JS API; `nativeplugin.go` — протокол; `pluginsdk/` — SDK. Если в отдельном проекте нет checkout YaJavis, используй [документацию upstream](https://github.com/newfpv/YaJavis/blob/main/docs/PLUGINS.md) и исходники совместимой версии: отсутствие соседних каталогов не требует менять структуру проекта. Не переноси внутренние методы официального провайдера в публичный API сторонних плагинов.

## Манифест и совместимость

Для официального плагина манифест находится в `plugins/<id>/plugin.json`, для отдельного репозитория — обычно в его корне. Минимальный ориентир для JS:

```json
{
  "id": "coin-demo",
  "name": "Монетка",
  "version": "1.0.0",
  "description": "Подбросить монетку голосовой командой.",
  "kind": "js",
  "main": "main.js",
  "api": 1,
  "category": "fun",
  "provides": ["commands", "tools"]
}
```

- `id` соответствует `^[a-z0-9][a-z0-9-]{1,31}$`, совпадает с каталогом официального плагина и сохраняется между версиями.
- Категория обязательна: `assistant`, `home`, `media`, `info`, `productivity`, `dev`, `fun`, `system` или `other`.
- Для native укажи `"kind": "native"` и, например, `"main": "coin-demo-{arch}"`. `main` — относительный путь внутри архива без `..` и обратных слешей. Официальный упаковщик требует имя файла **без подкаталога**, хотя общий загрузчик допускает подкаталоги.
- `provides` описывает реализованные возможности; произвольная строка сама по себе не добавляет обработку в ядро. Провайдеры VPN и умного дома требуют native.
- При выпуске повышай `version`; для возможностей более нового ядра задавай `min_core`. В официальном каталоге синхронизируй запись `plugins/index.json`, особенно `id` и `version`. Не включай автоматическую установку через `auto` без необходимости задачи.
- Поля `settings` описывают форму панели. Для токенов используй `type: "password"`; не включай секреты в манифест, логи или архив.

## JS: реализация и ограничения

Это goja, а не Node.js или браузер: нет `require`, `import`, DOM, файлов, процессов и `setTimeout`. Регистрируй обработчики при загрузке; сеть выполняй через синхронный `jarvis.fetch`, состояние сохраняй через `jarvis.store`, фоновые задачи — через `jarvis.every`.

```js
jarvis.command(["(подбрось|брось) монетку"],
  () => Math.random() < 0.5 ? "Орёл." : "Решка.");

jarvis.tool({
  name: "coin_demo_flip",
  description: "Подбросить монетку и вернуть орёл или решка.",
  parameters: { type: "object", properties: {} },
}, () => Math.random() < 0.5 ? "орёл" : "решка");
```

- Шаблоны команд используют Go/RE2 и сопоставляются со всей нормализованной фразой: без начального имени ассистента, в нижнем регистре, `ё` → `е`, без пунктуации. Обратный слеш в строке JS удваивается. Lookahead и обратные ссылки не поддерживаются.
- Строка из обработчика озвучивается; `""` означает выполнение с сигналом; `null`/`undefined` передают фразу дальше. Проверяй, что шаблоны не перехватывают чужие команды вроде «включи музыку» и «выключи свет».
- Имена инструментов начинай с префикса плагина, описывай аргументы JSON Schema. Не занимай имена инструментов ядра; актуальный список смотри в `isCoreTool` в `nativeplugin.go`.
- Загрузка ограничена 5 секундами, вызов — 20 секундами. `fetch` по умолчанию ждёт 15 секунд, допускает до 60, но это не отменяет лимит вызова. Ответ HTTP — до 2 МиБ, хранилище — до 256 КиБ, `every` — не чаще раза в 60 секунд. Ограничивай запросы и кеш; проверяй `response.ok` и ошибки JSON.
- Читай настройки из `jarvis.settings`, обрабатывай изменения через `jarvis.onSettings`. Для ожидаемых ошибок используй понятный `throw new Error(...)`, для состояния — `jarvis.status`.

## Native: SDK и жизненный цикл

В официальном Go-модуле используй импорт `github.com/newfpv/YaJavis/pluginsdk` и локальный `replace ... => ../../../pluginsdk`, как в существующих плагинах. Не добавляй зависимости плагина в `jarvisd/go.mod`.

- Создай `pluginsdk.New()`, зарегистрируй `OnInit`, `OnSettings`, `Tool`, `Command` и необходимые методы до `Run()`.
- Только JSON-сообщения протокола отправляются в stdout: одна строка — одно сообщение. Логи направляй в stderr или `p.Log`. Не запускай плагин обычным `go run .` для проверки протокола: SDK ожидает окружение и обмен с хостом.
- `init` должен ответить за 15 секунд, native-команда — за 3 секунды. На `shutdown` процесс должен быстро завершаться; не оставляй фоновые процессы.
- SDK обрабатывает запросы конкурентно: защищай общее состояние между командами, инструментами и обновлением настроек. Для собственных методов с отменой используй `HandleContext` и передавай его контекст в I/O; протокол поддерживает `deadline` и `cancel`. Не приписывай такую же сигнатуру API `Tool` или `Command`.
- Постоянные данные размещай в каталоге из `Init.Data`/`JARVIS_PLUGIN_DATA`. При обновлении сохраняются настройки, `data.json` и каталог `data/`; остальные файлы заменяются.
- Метод `core` и сервисные адаптеры `pluginsdk/services.go` обслуживают официальные провайдеры. Они не дают сторонним плагинам общего доступа к настройкам и учётным данным ядра.

Сборка обеих архитектур из `plugins/<id>/src/` (имя выходного файла согласуй с `main`):

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" -o ../coin-demo-arm64 .
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build -trimpath -ldflags="-s -w" -o ../coin-demo-armv7 .
```

Учитывай ограниченные память и место на колонке: избегай неограниченных очередей, кешей и горутин. Бинарные файлы не коммить.

## Проверки и упаковка

Выбирай проверки по изменённой части; не запускай сборку всех нативных плагинов ради правки одного JS-файла.

- JS: `node --check plugins/<id>/main.js` проверяет только синтаксис. Поведение проверяй через goja/тестовый хост в `jarvisd/plugins_test.go`, а не подменяй среду Node.js.
- В `jarvisd/`: `go test -run 'Test(JSPlugin|JSCommand|OfficialPlugins$|UnpackPlugin|PluginCatalog)' ./...`. Добавляй проверки новой команды, отказа от чужой фразы, настроек и ошибок API с локальным HTTP-сервером.
- В изменённом `plugins/<id>/src/`: `go vet ./...` и `go test -race ./...`; при изменении SDK выполни те же команды в `pluginsdk/`. Для изменений протокола проверь `TestNativePlugin` в `jarvisd/` и `TestProtocolDeadlineAndCancel` в SDK.
- Обычные тесты не должны требовать реальных ключей. Сетевые проверки запускай отдельно с `JARVIS_NET=1`, когда они нужны задаче.
- Официальная упаковка из корня: `go run scripts/pack-plugins.go build/plugins`. Она проверяет каталог и собирает **все** официальные native-плагины; Zig и payload установщика для этого не нужны. Результат: `plugin-<id>.zip` для JS или `plugin-<id>-arm64.zip`/`plugin-<id>-armv7.zip` для native.
- Для отдельного репозитория выполняй проверки и упаковку по [references/unofficial.md](references/unofficial.md). Не считай тесты официальных плагинов проверкой внешнего плагина, который в них не загружается.
- В ZIP должен быть `plugin.json` в корне или одной общей верхней папке, без ссылок и выхода за каталог. Лимиты: 24 МиБ архив, 48 МиБ распакованные файлы. Не упаковывай исходники native, локальные данные или секреты; для официального JS упаковщик включает все файлы его каталога.

Для ручной проверки устанавливай архив через «Плагины → Из файла» в согласованном окружении. В описании результата укажи команды проверок, место архива и оставшиеся ограничения. Отдельно отмечай, проверены ли установка, обновление с сохранением данных, перезапуск и голосовая команда на настоящей колонке.
