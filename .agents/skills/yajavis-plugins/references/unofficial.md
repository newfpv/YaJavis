# Неофициальный плагин в собственном репозитории

Используй этот файл вместе с общими правилами API из [SKILL.md](../SKILL.md). Здесь все пути и команды относятся к корню **репозитория плагина**. Выбери JS или native по задаче; отдельный репозиторий не требует переноса плагина в исходники YaJavis.

## Структура и манифест

Для нового проекта обычно достаточно одного плагина на репозиторий: загрузчик ищет архивы с фиксированными именами, без выбора `id` в имени архива.

```text
yajarvis-coin-demo/
├── plugin.json
├── main.js               # JS; для native вместо него — Go-исходники
├── README.md
└── .gitignore
```

У native-плагина исходники и `go.mod` могут лежать в корне или в `src/`; сохраняй принятую в проекте структуру. `bin/`, `build/` и `dist/` предназначены для результатов сборки и не коммитятся. Не создавай `plugins/index.json`: он нужен только официальному каталогу YaJavis.

Рекомендуемое имя репозитория — `yajarvis-<id>`, например `yajarvis-coin-demo`, а `plugin.json.id` — `coin-demo`. Каталог формирует предварительный ID из имени репозитория, убирая префикс `yajarvis-` или `jarvis-`, поэтому согласованность имён упрощает отображение и обновление. Требования к `id`, `api`, `category`, `settings` и `min_core` те же, что у официальных плагинов.

Укажи собственного автора, описание и `homepage` своего репозитория. `provides` перечисляет реально реализованные возможности; не копируй внутренний метод `core` из официальных провайдеров. Для стороннего native допустим `main` с подкаталогом: например, `"main": "bin/coin-demo-{arch}"`.

В README опиши команды, установку через «Из файла» и каталог, настройки и получение токенов, внешние сервисы, минимальную версию ядра, сборку и тесты. Данные и токены передаются через настройки плагина; ключи пользователя не должны становиться частью репозитория или ZIP.

## Зависимость от SDK для Go

Не копируй `replace ... => ../../../pluginsdk` из официальных плагинов: за пределами YaJavis такого пути нет. В новом проекте объяви собственный модуль и подключи SDK по проверенному коммиту либо существующему тегу модуля. Подставь реальные значения вместо заполнителей:

```sh
go mod init github.com/<owner>/yajarvis-coin-demo
go get github.com/newfpv/YaJavis/pluginsdk@<commit>
go mod tidy
```

В существующем проекте используй его `go.mod`, без повторного `go mod init`. Проверяй `go`-директиву SDK и требования зависимостей; не выдумывай номер опубликованной версии. Коммить `go.mod` и `go.sum`, чтобы сборка воспроизводилась без checkout YaJavis. Если для разработки самого SDK нужен локальный `replace`, не оставляй зависимость от личного абсолютного пути в публикуемом модуле.

Для native используй публичные методы `pluginsdk` из основного скилла. Запуск с `JARVIS_PLUGIN=1` сам по себе не заменяет хост: процесс ожидает `init`, регистрацию и последующие сообщения протокола.

## Проверки без привязки к монорепозиторию

- **JS**: `node --check main.js` проверяет синтаксис. Для поведения используй goja или реальный тестовый хост YaJavis, который явно загружает файлы этого плагина. В проекте без Go допустим отдельный тестовый модуль; не добавляй его только ради синтаксической проверки. Node-заглушка `jarvis` не доказывает совместимость с goja и Go/RE2.
- **Native**: из каталога Go-модуля выполняй `go vet ./...` и `go test -race ./...` на поддерживаемой хостовой платформе. Кросс-компиляцию для ARM проверяй отдельно от запуска тестов.
- Для новой функциональности проверь успешный запрос, неверные аргументы, отсутствие токена, ошибку внешнего сервиса, обновление настроек и отказ от чужой фразы. HTTP подменяй локальным сервером; обычные тесты не должны обращаться к платным API.
- При изменении native-протокола проверяй обмен через subprocess: `init`, ответ с исходным ID, `register`, вызов команды/инструмента и `shutdown`. Для методов через `HandleContext` добавляй deadline/cancel. Не заявляй, что отмена автоматически передаётся в `Tool` и `Command`.
- В CI достаточно проверок самого плагина, соответствующего Go-модуля и обоих ARM-артефактов. Не запускай корневой `build.sh` или упаковщик официальных плагинов YaJavis для сборки внешнего проекта.

## ZIP и сборка

Имена файлов в релизе имеют значение: загрузчик сначала ищет `jarvis-plugin-<arch>.zip`, затем `jarvis-plugin.zip`. Официальные имена `plugin-<id>*.zip` для отдельного репозитория не подходят.

Для JS с `main: "main.js"`:

```sh
mkdir -p dist
zip dist/jarvis-plugin.zip plugin.json main.js
```

Если плагину нужны дополнительные ресурсы, включай их явно. Создавай архив заново при каждом выпуске: дописывание существующего ZIP может сохранить удалённые файлы. Не архивируй весь рабочий каталог вместе с `.git`, тестовыми секретами и локальным состоянием.

Для Go-проекта с модулем в корне и `main: "bin/coin-demo-{arch}"`:

```sh
mkdir -p build/arm64/bin build/armv7/bin dist
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" -o build/arm64/bin/coin-demo-arm64 .
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build -trimpath -ldflags="-s -w" -o build/armv7/bin/coin-demo-armv7 .
cp plugin.json build/arm64/
cp plugin.json build/armv7/
(cd build/arm64 && zip -r ../../dist/jarvis-plugin-arm64.zip plugin.json bin)
(cd build/armv7 && zip -r ../../dist/jarvis-plugin-armv7.zip plugin.json bin)
```

Это примеры для ID `coin-demo`: согласуй пути с настоящим манифестом. Используй чистые staging-каталоги и новые архивы; для модуля в `src/` скорректируй рабочий каталог и пути вывода. Можно собрать один `jarvis-plugin.zip` с обеими программами, но отдельные ZIP уменьшают загрузку и расход места на колонке.

Внутри каждого архива должны быть `plugin.json` и файл, на который указывает `main` после подстановки архитектуры. Допустима одна общая верхняя папка, но корень архива проще. Лимиты: 24 МиБ ZIP, 48 МиБ распакованных файлов. Допускаются обычные файлы без ссылок и выхода за каталог. Перед выпуском проверь список содержимого и что в каждом native-архиве лежит Linux-бинарник нужной архитектуры.

## Каталог GitHub и выпуск

Для обнаружения каталогом нужен публичный репозиторий с темами:

- `yajarvis-plugin` — тема, по которой ищет ядро;
- `yajarvis-<category>`, например `yajarvis-fun`, — та же категория, что в манифесте. Без распознанной темы категория в каталоге будет `other`.

Одних исходников или автоматически созданного GitHub source ZIP недостаточно: приложи архивы с указанными выше именами как release assets. Ядро обращается к `/repos/<owner>/<repo>/releases/latest`, а не скачивает ветку репозитория; проверь, что нужный выпуск возвращается этим API. Версию манифеста повышай и согласуй с тегом выпуска, например `1.2.0` и `v1.2.0`. Настройки, `data.json` и `data/` должны сохраняться при обновлении; остальные файлы могут заменяться.

Создание репозитория, изменение тем, push тега и публикация релиза выполняются только в рамках поручения пользователя. Если запрошена лишь разработка, подготовь исходники, тесты и локальные архивы и сообщи, что нужно для публикации. CI для релизов также настраивай под задачу, без секретов в исходниках.

Каталог кешируется примерно на час, поиск GitHub может обновляться с задержкой. Если плагин не виден, проверь тему, публичность и состояние репозитория (архивные пропускаются), обнови каталог. Если карточка есть, но установка не работает, проверь `releases/latest`, имена assets, лимиты ZIP, `plugin.json`, `main`, `api` и `min_core`.

Для локальной установки релиз GitHub не требуется: используй «Плагины → Из файла». Повторная установка того же `id` заменяет код с сохранением настроек и данных. Проверь отдельно включение, изменение настроек, перезапуск, обновление и голосовую команду на колонке; автотесты и кросс-компиляция этого не подтверждают.
